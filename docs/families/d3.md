# Family: d3

> The Decision 3.0 family (`vllm-sr/d3` and its five siblings, Apache-2.0)
> prompts every question as a chat-template decision block whose options
> each carry a single-token answer code, runs one **noncausal** forward
> pass — the causal mask is lifted in the full-attention layers — and reads
> a separate 255-row float32 readout matrix at the final prompt position
> (`d3-code-readout-v1`, shipped as `decision_config.json` beside every
> checkpoint). No token is ever sampled.

## Status in openkind

**Rust-loadable (prototype profile).** The pinned profile
`d3-edge:664f9ead734372935286` serves `vllm-sr/d3-edge` at
`18d61df78684675463af9ae732872478845c5a79` — the `v3.1.0` release commit
the Decision Index board and the vLLM semantic-router parity record
evaluated (the Hub tag of the same name points elsewhere; weight and
readout blobs are byte-identical to the surveyed HEAD, which only edited
runtime server files). The checkpoint is a pruned 12-layer Qwen3.5-0.8B
hybrid (1024/3584) plus a `[255, 1024]` float32 `readout.safetensors`.

The loader verifies every artifact by SHA-256 in place (`config.json`,
`decision_config.json`, `tokenizer.json`, `tokenizer_config.json`,
`chat_template.jinja`, `readout.safetensors`, and the checkpoint shard),
executes the shared native FP32 CPU backbone
([`qwen35/backbone`](../../crates/openkind-backends/src/qwen35/backbone/))
with the profile's **noncausal** geometry and the text-only
`language_model.` tensor namespace, and applies the code readout at the
final prompt position. It serves through `openkindd` via
`--d3-aliases` / `--d3-model-root` and is benchmarked through
`openkind-bench score --engine d3-edge`. It is catalog-installable
offline-first: `openkind pull d3-edge:664f9ead734372935286` (alias
`d3:edge`) downloads the pinned artifacts and verifies each digest.

Profile semantics:

- Probability space: `ConditionalOnOfferedOptions` — the temperature-1.0
  softmax over the offered options' code logits sums to one. An offered
  `__none__` key is scored as an ordinary option.
- Continuation state: none. The noncausal mask also means a question can
  never reuse another row's full-attention KV: `repeated_full` is the only
  legal execution strategy, and the family retains nothing between
  requests.
- Text generation: none.
- Vision: the checkpoint ships a vision tower that this family does not
  execute; text questions only.

## What the family adds to the shared backbone

Three checkpoint facts required backbone-side changes, all pinned by
`decision_config.json` and `config.json` contract checks:

1. **Noncausal full attention.** `attention_mode:
   noncausal_full_attention` lifts the causal mask so every position sees
   the whole prompt. [`Qwen35Geometry`] carries a `causal` flag (every
   published base checkpoint is causal) and the grouped-query kernel
   branches to `past_rows + rows` visible keys; rotary positions stay
   absolute, and the gated-DeltaNet layers keep their causal scan. The
   kernel branch is pinned against a naive bidirectional reference in
   [`layer0_tests.rs`](../../crates/openkind-backends/src/qwen35/backbone/layer0_tests.rs).
2. **Per-layer mixer table.** The 12-layer prune keeps an irregular
   `layer_types` subset (full attention at layers 2, 5, 8, 9, 10, 11), so
   [`Qwen35Geometry`] now carries the explicit per-layer table instead of
   deriving it from the declared 3:1 interval, which the config still
   states.
3. **Text-only tensor namespace.** `Qwen3_5Model` checkpoints nest under
   `language_model.` without the `model.` prefix of the
   `Qwen3_5ForConditionalGeneration` releases; the backbone takes the
   namespace at construction and the embedding layout reads the table by
   name.

## Reference evidence

- **Prompt byte-parity.** The rendered prompts of seven fixture cases
  (choice narrow/wide, choice with `__none__`, noul with default and
  described criteria, score levels, the `(empty)` state placeholder) were
  tokenized with the pinned `tokenizer.json` on both sides: the Rust
  renderer and the shipped reference (`d3_format.py` over the checkpoint's
  real `chat_template.jinja`, executed with a jinja2 shim) produce
  **byte-identical token sequences** for all seven cases. The reference
  run and its per-case hashes are recorded in
  [`research/handoffs/registry-expansion-2026-10-12/d3-edge-reference-prompts.json`](../../research/handoffs/registry-expansion-2026-10-12/d3-edge-reference-prompts.json);
  the engine-side stats are pinned in the golden fixture
  (`prompt_stats`). Two wire-representation differences are declared, as
  in the other surveyed families: Choice options render in the wire's
  sorted label order, and object states serialize in the wire's hash-key
  order (the comparison protocol supplies the reference the same canonical
  inputs).
- **Code table.** `decision_config.json` pins the 255 answer codes and
  token ids; the loader derives the table with the reference algorithm
  (`A..Z` then single-token two-letter uppercase strings, each verified
  stable after the assistant generation prompt) and fails closed on any
  divergence from the pinned table. The derivation was additionally
  verified against the checkpoint's real vocabulary.
- **Golden replay.** `crates/openkind-backends/tests/d3_edge_parity.rs`
  replays the committed golden fixture against the pinned checkpoint
  (env-gated via `OPENKIND_D3_MODEL_ROOT`); the always-on tests pin the
  profile constants, the derivation contract, and the fail-closed load
  paths. No torch cross-check ran for the forward pass: the reference
  runtime needs the flash-linear-attention kernels, which are CUDA-only.
  The backbone kernels themselves are the parity-verified CPU oracle the
  other qwen3.5 families serve through, and the answer distributions on
  the fixture cases behave as the state text implies.
