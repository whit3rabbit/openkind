# Family: d3

> The Decision 3.0 family (`vllm-sr/d3` and its five siblings, Apache-2.0)
> prompts every question as a chat-template decision block whose options
> each carry a single-token answer code, runs one **noncausal** forward
> pass (the causal mask is lifted in the full-attention layers), and reads
> a separate 255-row float32 readout matrix at the final prompt position
> (`d3-code-readout-v1`, shipped as `decision_config.json` beside every
> checkpoint). No token is ever sampled.

The 0.8B profiles carry a separate `[255, 1024]` float32
`readout.safetensors`, nano a `[255, 2048]` one, mini a `[255, 2560]` one,
flash a `[255, 4096]` one; all pin their artifacts by SHA-256 in place.
d3-mini and d3-flash share a chat template
that inverts the thinking conditional relative to the smaller siblings,
which renders the same empty `<think>` block for the reference's
`enable_thinking=False` calls; each profile pins its own template digest.

The loader verifies every artifact by SHA-256 in place (`config.json`,
`decision_config.json`, `tokenizer.json`, `tokenizer_config.json`,
`chat_template.jinja`, `readout.safetensors`, and the checkpoint shard),
executes the shared native FP32 CPU backbone
([`qwen35/backbone`](../../crates/openkind-backends/src/qwen35/backbone/))
with the profile's **noncausal** geometry and the text-only
`language_model.` tensor namespace, and applies the code readout at the
final prompt position.

Every profile serves through `openkindd`. The short names `edge`, `lite`,
`nano`, `mini`, and `flash` key both daemon flags, for example
`--d3-aliases "edge=<alias>;flash=<alias>"` with
`--d3-model-roots "edge=<path>;flash=<path>"`. Each profile is benchmarked
through `openkind-bench score --engine d3-<short>` (`d3-edge`, `d3-lite`,
`d3-nano`, `d3-mini`, `d3-flash`). Each is catalog-installable through
`openkind pull <profile>` with the alias `d3:<short>` (for example
`openkind pull d3-edge:664f9ead734372935286` or `openkind pull d3:flash`),
which downloads the pinned artifacts and verifies each digest.

Profile semantics:

- Probability space: `ConditionalOnOfferedOptions`. The temperature-1.0
  softmax over the offered options' code logits sums to one. An offered
  `__none__` key is scored as an ordinary option.
- Question validation follows the reference `normalize_question`: Choice
  takes 1 to 255 options with nonempty keys (a single option reads a
  one-code softmax), and Score takes 2 to 10 distinct, nonempty levels.
- Work limits: a question's rendered prompt is capped at 65,536 tokens and
  the sum over a request's questions at 262,144 tokens. Both are stricter
  than the reference runtime, which applies only the optional
  `decision_config.json` `max_length` (null in the vendored d3-edge package
  manifest, leaving the checkpoint's 262,144-token context) and has no
  request-level cap. The engine renders, validates, and counts
  every question before the first forward, so an over-limit request is
  rejected without model work. Nothing is truncated. The rejection is
  invalid input (HTTP 422 `invalid_body`, gRPC `INVALID_ARGUMENT`), like
  the family's other request-validation errors; the reference reports
  `max_length_exceeded`. Deadlines and disconnects are checked inside each
  full-attention kernel as well as between layers.
- Continuation state: none. The noncausal mask also means a question can
  never reuse another row's full-attention KV: `repeated_full` is the only
  legal execution strategy, and the family retains nothing between
  requests.
- Text generation: none.
- Vision: the checkpoint ships a vision tower that this family does not
  execute; text questions only.

## What the family adds to the shared backbone

Three checkpoint facts required backbone-side changes, all pinned by
`decision_config.json` and `config.json` contract checks:

1. **Noncausal full attention.** `attention_mode:
   noncausal_full_attention` lifts the causal mask so every position sees
   the whole prompt. [`Qwen35Geometry`] carries a `causal` flag (every
   published base checkpoint is causal) and the grouped-query kernel
   branches to `past_rows + rows` visible keys; rotary positions stay
   absolute, and the gated-DeltaNet layers keep their causal scan. The
   kernel branch is pinned against a naive bidirectional reference in
   [`layer0_tests.rs`](../../crates/openkind-backends/src/qwen35/backbone/layer0_tests.rs).
   A cached prefix never attended to its suffix, so noncausal full
   attention refuses cached keys and values, and the paths that hard-code
   the causal uniform layout (MLX, continuation-state persistence, the
   pinned architecture contract) fail closed on any other geometry.
2. **Per-layer mixer table.** The 12-layer prune keeps an irregular
   `layer_types` subset (full attention at layers 2, 5, 8, 9, 10, 11), so
   [`Qwen35Geometry`] now carries the explicit per-layer table instead of
   deriving it from the declared 3:1 interval, which the config still
   states.
3. **Text-only tensor namespace.** `Qwen3_5Model` checkpoints nest under
   `language_model.` without the `model.` prefix of the
   `Qwen3_5ForConditionalGeneration` releases; the backbone takes the
   namespace at construction and the embedding layout reads the table by
   name.

## Reference evidence

- **Prompt byte-parity.** The rendered prompts of seven fixture cases
  (choice narrow/wide, choice with `__none__`, noul with default and
  described criteria, score levels, the `(empty)` state placeholder) were
  tokenized with the pinned `tokenizer.json` on both sides: the Rust
  renderer and the shipped reference (`d3_format.py` over the checkpoint's
  real `chat_template.jinja`, executed with a jinja2 shim) produce
  **byte-identical token sequences** for all seven cases, for each of the
  five pinned profiles. The reference runs and their per-case hashes are
  recorded in
  [`research/handoffs/registry-expansion-2026-10-12/d3-edge-reference-prompts.json`](../../research/handoffs/registry-expansion-2026-10-12/d3-edge-reference-prompts.json),
  [`d3-lite-reference-prompts.json`](../../research/handoffs/registry-expansion-2026-10-12/d3-lite-reference-prompts.json),
  [`d3-nano-reference-prompts.json`](../../research/handoffs/registry-expansion-2026-10-12/d3-nano-reference-prompts.json),
  [`d3-mini-reference-prompts.json`](../../research/handoffs/registry-expansion-2026-10-12/d3-mini-reference-prompts.json),
  and
  [`d3-flash-reference-prompts.json`](../../research/handoffs/registry-expansion-2026-10-12/d3-flash-reference-prompts.json).
  The same token counts and token-id digests are pinned in each golden
  fixture (`prompt_stats`), computed through the engine's own planner.
  Two wire-representation differences are declared, as
  in the other surveyed families: Choice options render in the wire's
  sorted label order, and object states serialize in the wire's hash-key
  order (the comparison protocol supplies the reference the same canonical
  inputs).
- **Code table.** `decision_config.json` pins the 255 answer codes and
  token ids; the loader derives the table with the reference algorithm
  (`A..Z` then single-token two-letter uppercase strings, each verified
  stable after the assistant generation prompt) and fails closed on any
  divergence from the pinned table. The derivation was additionally
  verified against the checkpoint's real vocabulary.
- **Golden replay.** The goldens are Rust self-replay: the fixture
  generator recorded this engine's own answers, so a replay detects drift
  in the Rust path, not disagreement with the reference forward pass. No
  forward-pass cross-check against the BF16 reference runtime ran; it needs
  the flash-linear-attention kernels, which are CUDA-only. The backbone
  kernels are the parity-verified CPU oracle the other qwen3.5 families
  serve through. What was checked against the reference is the prompt
  byte-parity above; a replay checks agreement with the recorded Rust
  answers within a probability tolerance of 0.005.
- **Tests.** [`d3_edge_parity.rs`](../../crates/openkind-backends/tests/d3_edge_parity.rs)
  always runs the profile-constant checks, the code-table derivation over
  the vendored tokenizer sample, the golden fixtures' internal consistency
  (each case's usage equals its reference-anchored `prompt_stats` token
  count), and the fail-closed loads: missing artifacts, and dummy
  artifacts that fail the first (`config.json`) digest check for every
  profile. With `OPENKIND_D3_MODEL_ROOT` set, it also replays the golden,
  asserts each case's `prompt_stats` against the real tokenizer, and
  checks a staged `decision_config.json` drift. Replay another profile by
  naming its fixture directory:

  ```bash
  OPENKIND_D3_MODEL_ROOT="<pinned-d3-root>" \
  OPENKIND_D3_FIXTURE=d3_<profile-id> \
    env -u RUST_LOG cargo test -p openkind-backends --test d3_edge_parity \
    golden_replay_matches_the_pinned_checkpoint -- --exact --nocapture
  ```

  An unset or nonexistent root skips the replay with a message; a skipped
  replay is not checkpoint parity evidence.

## Benchmarks

Measured request-path benchmarks are pending; every profile ships with
research status and no task-quality claim. `openkind-bench score --engine
